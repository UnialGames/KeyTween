# 성능

KeyTween이 Animator, DOTween, LitMotion과 비교해 어느 정도 성능을 내는지와, 사용할 때 알아 둘 점을 설명합니다. 값은 2026-10-15~16에 측정했습니다.

* 전체 결과 표: [`Benchmarks.md`](Benchmarks.md)

## 1. 결론

IL2CPP 릴리스 빌드에서 오브젝트 2,000개로 잰 결과를 요약합니다.

### 결과 표

괄호 안의 값은 같은 값을 스크립트로 직접 넣는 경우(기준)보다 더 든 시간이며, 이것이 그 방식 자체의 비용입니다.

| | KeyTween | DOTween Pro | LitMotion | Animator | AnimationUI |
|---|---:|---:|---:|---:|---:|
| 맥박 반복 (ms) | 7.69 (+0.38) | 7.71 (+0.40) | **7.66 (+0.34)** | 10.16 (+2.85) | 9.31 (+2.00) |
| 목록 등장 (ms) | 1.70 (+0.04) | 1.59 (−0.06) | **1.53 (−0.13)** | 5.23 (+3.57) | 2.18 (+0.52) |
| 글자 물결 100개 (ms) | **0.61** | 2.11 | 2.05 | 지원 안 함 | 지원 안 함 |
| 매 프레임 GC (기준 대비) | **0** | 맥박 0, 등장 +11KB | **0** | +0.1KB | +16KB |

한 번 실행한 값이므로 경우마다 ±5% 정도 흔들립니다. 방식 사이에 0.1ms 안쪽으로 나는 차이는 이 범위에 들어갑니다.

### 강점

* **Animator와 AnimationUI보다 빠릅니다.** 맥박 2,000개에서 자체 비용이 약 1/5~1/7입니다(+0.38ms 대 +2.0~2.9ms).
* **코드 트윈과 같은 수준입니다.** 맥박 2,000개에서 DOTween Pro(+0.40), LitMotion(+0.34)과의 차이가 0.05ms 안쪽입니다. 코드 트윈은 DOTween, LitMotion처럼 코드로 연출을 만드는 라이브러리입니다.
* **글자 효과는 가장 빠릅니다.** 텍스트 100개에서 DOTween Pro와 LitMotion의 약 1/3입니다.
* **재생 중 GC 할당이 없습니다.** DOTween은 반복 재생할 때마다 할당합니다(목록 등장 2,000개 기준 프레임당 11KB). AnimationUI도 코루틴 때문에 매번 할당합니다.

### 약한 곳: 재생 시작 비용

목록 등장에서 2,000개를 한 번에 다시 재생하는 데 드는 시간입니다.

* KeyTween: 2.31ms
* LitMotion: 1.34ms
* DOTween: 3.89ms

이 차이는 한 프레임에 수천 개를 동시에 시작할 때만 드러납니다. 자세한 내용은 아래 [재생을 시작하는 비용](#재생을-시작하는-비용)을 참고하세요.

### 목록 등장에서 음수가 나오는 이유

목록 등장에서 기준보다 빠른 값(음수)이 나오는 것은 측정 방식 때문입니다. 기준 스크립트는 연출이 끝난 뒤에도 매 프레임 값을 계속 넣지만, 라이브러리들은 0.4초 뒤에 멈춥니다. 그 구간에서는 기준이 더 많은 일을 하므로, 0 근처의 값은 "차이 없음"으로 보면 됩니다.

## 2. 측정 방법

모든 방식을 같은 조건에서 비교했습니다.

### 비교 방식

같은 오브젝트(이미지 N개, 텍스트 N개)에 같은 연출을 방식별로 붙였습니다.

* 맥박 반복
* 목록 등장 (0.5초마다 다시 재생)
* 글자 물결

기준(직접 대입)은 애니메이션 시스템 없이 스크립트 하나가 매 프레임 같은 값을 넣는 방식입니다. uGUI가 다시 그리는 비용은 모든 방식에 똑같이 들어 있으므로, 기준과의 차이가 각 방식의 비용입니다.

### 환경

* Windows 64비트 플레이어, 1280×720 창 모드
* VSync 끔, 프레임 제한 없음
* 경우마다 1초 예열한 뒤 4초 동안 매 프레임 기록
* CPU: AMD Ryzen 7 7800X3D
* Unity: 6000.6.3f1

### 시간과 GC

* **시간**: 릴리스 빌드(Mono, IL2CPP)의 프레임 시간
* **GC**: 개발 빌드로 따로 측정. 할당 카운터(`GC Allocated In Frame`)가 개발 빌드에서만 동작합니다.

## 3. 사용할 때 알아 둘 점

KeyTween을 많이 쓰는 화면에서 성능에 영향을 주는 점입니다.

### 재생하지 않을 때의 비용

재생 중이 아닌 KeyTween은 매 프레임 아무 일도 하지 않습니다. 화면에 KeyTween이 많아도 재생하는 것만 비용이 듭니다.

### 재생 중 GC 할당

재생 중에는 GC 할당이 없습니다. 반복 상태를 계속 재생하거나 같은 상태를 여러 번 다시 재생해도 같습니다. 자식 호출이 있는 상태도 같습니다.

예외는 바깥 Prefab이 트랙을 덮어쓴(오버라이드) 자식 상태를 부르는 상태입니다. 이 상태는 재생할 때마다 길이를 구하면서 덮어쓴 자식 상태를 새로 합칩니다.

### With와 Build

`With(state)`와 `Build(state)`는 부를 때마다 객체를 새로 만듭니다. 그래서 재생할 때마다 `With(...)`를 다시 쓰면 그만큼 할당이 생깁니다.

* `With`가 돌려준 `KeyTweenPlay`는 필드에 두고 다시 재생하세요. 다시 쓰면 재생할 때 할당이 없습니다.
* `Build`는 상태를 처음 만들 때 한 번 부르고, 그 뒤에는 `Play("이름")`으로 재생하세요.

### Burst로 계산되는 트랙

키가 모두 이징 프리셋인 트랙은 재생 중인 모든 트랙을 모아 Burst로 한 번에 계산합니다. 다음 트랙은 관리 코드에서 하나씩 계산하므로 조금 더 느립니다.

* AnimationCurve 키
* Punch, Shake 키
* 글자별 트랙
* 무작위 글자(scramble) 노출

같은 연출을 수천 개에 붙인다면 이징 프리셋으로 만드는 편이 빠릅니다. Burst를 쓰기 위해 `com.unity.burst`가 함께 설치됩니다.

### 재생을 시작하는 비용

재생을 시작할 때 키를 Burst 계산용으로 묶는 작업이 있습니다. 2,000개를 한 프레임에 다시 재생하면 IL2CPP에서 2.31ms가 듭니다.

* 보통 화면에서는 드러나지 않습니다.
* 수천 개를 같은 프레임에 시작한다면 몇 프레임에 나눠 시작하세요.

### 글자 효과

글자 트랙이 있는 텍스트는 매 프레임 다시 배치하지 않고, 처음 배치한 결과에 글자별 변형만 적용합니다. 다음 경우에만 다시 배치합니다.

* 텍스트, 크기, 색, 노출 글자 수가 바뀔 때
* 글자 수가 바뀔 때
* 텍스트 상자 크기가 바뀔 때

재생 중에 텍스트를 자주 바꾸면 그때마다 배치 비용이 듭니다.

### 처음 만들 때의 할당

KeyTween을 처음 재생할 때 Burst 계산용 배열을 한 번 확보합니다. 상태 2,000개에서 약 1.2~1.4MB이며, 그 뒤 재생 중에는 할당이 없습니다.

[벤치마크](Benchmarks.md#준비setup-할당)의 준비 할당(KeyTween 2,000개에 약 6.6MB)은 이 값과 다릅니다. 그 측정은 상태를 코드로 만드는 비용까지 포함하기 때문입니다.
